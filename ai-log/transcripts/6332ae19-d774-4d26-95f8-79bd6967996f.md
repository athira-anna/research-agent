## 🤖 Claude

Your five steps are a reasonable start. I'd change four things before designing any single stage.

## What I'd change

**1. Your steps 2 and 3 are really two different kinds of work.**
- "Extract main details" is about removing page clutter (menus, ads, cookie banners). Ordinary code does this well, for example the `trafilatura` library. It belongs with fetching, and it doesn't need an LLM.
- "Identify claims" is the actual LLM work.

Splitting them this way means the LLM steps only ever see clean text.

**2. There's a missing step between per-source extraction and cross-referencing: aligning claims.**
Your step 4 would have to compare every claim from every source against every other. That is the "giant one-shot prompt" the evaluators warn about. Before you can spot a contradiction, you need to know that source A's "costs fell 40%" and source C's "prices are up" are about the same thing. So:
- First group claims across sources by sub-topic.
- Then judge each group on its own: do the sources agree, contradict each other, or add nuance?

This alignment step is the hard part the problem statement points at, so it should be its own stage.

**3. Finding gaps needs a reference list, so add a planning step at the start.**
"Claims no source addresses" can't be found without knowing what *should* have been addressed. A small first step turns the topic into a list of 5–8 key questions or aspects. That list then does three jobs:
- It's the checklist for finding gaps.
- It gives claim extraction tags to attach to each claim.
- It gives alignment ready-made groups.

**4. Make failure and grounding part of the data that flows through.**
- Each source carries a status (`ok`, `paywalled`, `js_blocked`, `empty`, `off_topic`) all the way into the brief. The brief then says "Source 3 was paywalled; findings rest on 4 sources" rather than failing silently.
- After extraction, check that each claim's quoted text actually appears in the source. It's cheap, easy to defend, and it catches made-up citations.

## Proposed components

| # | Stage | Kind | Output |
|---|---|---|---|
| 0 | **Plan**: topic → key questions to cover | LLM, 1 call | `plan.json` |
| 1 | **Acquire**: fetch with fallbacks (plain HTTP → headless browser → reader service) and cache | Code | `raw/<id>.html` plus a status per source |
| 2 | **Clean and triage**: pull out the main text; detect paywalls, empty pages and off-topic pages | Code (one optional LLM relevance check) | `sources.json` |
| 3 | **Extract claims**: one call per source, run in parallel. Each claim gets a quote, a question tag and a type (fact / number / opinion / forecast), then the quote check | LLM, N calls | `claims.json` |
| 4 | **Align**: group claims across sources by question into shared claim groups | LLM | `clusters.json` |
| 5 | **Judge**: per group, label agree / contradict / nuance. Consensus vs. outlier comes from counting sources in code; gaps are questions with no claims | LLM per group, plus code | `analysis.json` |
| 6 | **Write the brief**: fill a fixed template from the analysis; the LLM writes only the executive summary | Code + 1 LLM call | `brief.md` (+ JSON) |

Every stage writes its result to a `runs/<id>/` folder. That generalises your caching idea: you can re-run any single stage, debug it, and step through the files in the Loom demo.

## On Google ADK + MCP

- **ADK itself is fine.** Its sequential and parallel agent types map directly onto stages 0→6, with stage 3 running in parallel. One thing to check: ADK is built Gemini-first, and using it with Claude or other models goes through LiteLLM.
- **I'd skip MCP for fetching and cleaning.** MCP is useful for sharing tools between different clients. Here it adds a separate server process and more setup for no gain within a 2-hour budget. Plain Python function tools are simpler.
- **I'd also not let an LLM decide when to fetch.** Fetching and cleaning should run in a fixed order in code. The one place an agent's judgment helps is retrying a failed source: switch to the browser or reader fallback, or mark it unavailable. That choice is easy to defend in the walkthrough: "the steps are fixed code, and the LLM is used only where judgment is needed."

Yes, that's the main weakness of grouping claims only by question. Your two answers don't contradict each other. They answer the same question for **different groups of people**. If we only group by question, stage 5 would either call them a contradiction or average them into nonsense.

Your idea of defining a coverage group is right. I'd make it explicit as a **scope** attached to every claim.

## Every claim gets a scope

Whatever a claim says, its scope is the conditions under which it's true. A few general dimensions cover almost every topic:

| Dimension | Example |
|---|---|
| **Population / segment** | software professionals, healthcare workers |
| **Geography** | US, EU, global |
| **Timeframe** | 2023–2025, "by 2030" |
| **Metric** | job loss %, jobs displaced (count), roles exposed to AI |

The **metric** dimension is the one people miss, and it causes the most false contradictions. "30% of jobs exposed to AI" and "2% of jobs lost to AI" look contradictory, but they measure different things. Research topics are full of these.

## Where the scope dimensions come from: both places

- **Fixed dimensions on every claim:** stage 3 always fills in population, geography, timeframe and metric (or "unspecified"). The planner can't predict everything a source will talk about, so this keeps the format predictable.
- **Planner-suggested facets per question:** stage 0 adds the expected breakdowns for each question. For your example: *"by sector, by region"*. These tell extraction which values to look for and how to name them.

## How stage 4 changes

Within each question, group claims a second time, by scope:

```
Q: What % of jobs are lost due to AI?
 ├─ [software, US, 2024, job-loss %]   → A: +10%,  C: +12%      → compare
 ├─ [healthcare, US, 2024, job-loss %] → B: −5%                 → single-source claim
 └─ [all sectors, global, exposure %]  → D: 30% exposed         → different metric, not compared
```

As part of this, the LLM also standardises the scope values, so "tech workers" and "software engineers" fall into the same bucket. This needs judgment, so it's an LLM job, but it's limited to one question at a time.

## Stage 5's labels get richer

| Same scope? | Values agree? | Label |
|---|---|---|
| Same scope | Yes | **Consensus** |
| Same scope | No | **Contradiction**, the real kind |
| Partly the same (US tech vs. global tech) | No | **Tension / nuance**: "differences may be due to scope" |
| Different scope | n/a | **Complementary**, reported side by side |
| Only one source | n/a | **Outlier / single-source** |

Two extra benefits:
- **Apparent contradictions that turn out to be scope differences** are worth flagging in their own right ("headlines disagree, but the sources measure different things"). That's the cross-source reasoning the evaluators are looking for.
- **Gaps get finer.** Comparing found scopes against the planner's facets gives "no source covers healthcare outside the US", not just "no source covers this question".

## One thing to watch

Sources often leave scope out ("AI will cut 10% of jobs", with no who, where or when). Store that as `unspecified`, and treat an unspecified scope as only *partly* overlapping with anything else. That means it can produce "tension" but never a confident "contradiction". It's a conservative rule that's easy to defend.

# Claim format (output of stage 3)

## What counts as one claim

**One claim is one checkable statement, about one question, under one scope.**
- A compound sentence is split up. "AI cut software jobs 10% but boosted healthcare hiring" becomes 2 claims.
- Background, definitions and marketing filler are skipped.
- At most ~15 claims per source, with the most topic-relevant first. This keeps the cross-source stages manageable.
- A claim that doesn't fit any planned question goes to `question_id: "other"`, not the bin. Unexpected single-source claims are often the most interesting.

## Fields

```json
{
  "claim_id": "s2-c04",
  "source_id": "s2",
  "question_id": "q1",
  "statement": "AI-related job losses among US software professionals rose 10% in 2024.",
  "claim_type": "statistic",
  "value": { "number": 10, "unit": "percent", "direction": "increase" },
  "scope": {
    "population": { "raw": "software developers", "canonical": null },
    "geography":  { "raw": "United States",       "canonical": null },
    "timeframe":  { "raw": "last year (2024)", "start": 2024, "end": 2024 },
    "metric":     { "raw": "jobs lost to automation", "canonical": null }
  },
  "certainty": "asserted",
  "evidence": {
    "quote": "verbatim sentence(s) from the cleaned source text",
    "attributed_to": "McKinsey Global Institute, 2024 survey"
  },
  "grounded": true
}
```

| Field | Why it's there |
|---|---|
| `claim_type`: statistic / fact / forecast / opinion / causal | A forecast and a statistic don't contradict each other. Opinions are reported, never counted towards consensus. |
| `value` (only when there's a number) | Lets code compare numbers and directions. The LLM isn't asked whether 10% and 12% "agree". |
| `scope.*.raw` / `canonical` | Stage 3 copies the source's wording into `raw`. Stage 4 fills `canonical` when grouping. Keeping both lets us check that standardisation didn't distort anything. |
| `certainty`: asserted / hedged / reported | "AI *may* cut jobs" against "AI *did not* cut jobs" is a tension, not a hard contradiction. |
| `evidence.quote` | The citation in the brief. It's also what the quote check matches against the source text. |
| `evidence.attributed_to` | **Important for consensus.** If 3 articles all repeat one McKinsey number, that's one origin, not 3 independent sources agreeing. Stage 5 counts independent origins and says so. |
| `grounded` | Set by code, not the LLM. A claim whose quote isn't in the source gets dropped, or shown with a warning. |

There is deliberately **no LLM self-confidence score**. Those numbers aren't calibrated, so I'd find them hard to defend.

## What stage 0 gives stage 3

```json
{ "id": "q1", "text": "What share of jobs is being lost to AI?",
  "facets": ["sector", "region"], "metrics": ["job loss %", "jobs displaced", "exposure %"] }
```

The planner's metrics list nudges extraction to record *which* metric a source uses. That's what stops "30% exposed" and "2% lost" from being counted as a contradiction.

## 1. Dropped claims

- They go to `runs/<id>/dropped_claims.json`, each with `claim_id`, `source_id`, the claimed `quote` and the `reason` (e.g. `quote_not_found`, `best_match_score: 0.41`).
- The brief's source-status section shows the count for each source, e.g. *"s3: 12 claims extracted, 2 dropped (quote not found in source)"*.

## 2. Claim type: yes, the categories overlap

"AI caused a 10% drop in jobs" is a statistic *and* causal *and* observed. One field was mixing three separate questions. Replace it with three independent fields:

| Field | Question it answers | Values |
|---|---|---|
| `modality` | Is it a measurement, a prediction or a judgment? | `observed` / `forecast` / `opinion` (only one applies) |
| `causal` | Does it say X causes Y? | `null` or `{ "cause": "AI adoption", "effect": "job losses" }` |
| `value` | Does it contain a number? | `null` or the number object (below) |

Plus `certainty` (asserted / hedged / reported), as before. "Statistic" stops being a type: a claim is a statistic if `value` isn't null.

Making causality a separate field also exposes a kind of contradiction we'd otherwise miss: **same number, different cause**. "Software job losses rose 10%, driven by AI" against "rose 10%, driven by interest rates" agree on the figure but disagree on the cause. Stage 5 can flag that as a contradiction about the cause.

## 3. Numbers: this needs to be in the format, not only the code

Your instinct is right, and here's why it belongs in the format. **Stage 3 is the only stage that sees the original sentence.** If extraction stores a bare "10%", nothing later can recover whether it meant a share, a change in points or a relative change. So the format captures *what the number means*, and the code does the maths.

```json
"value": {
  "raw": "rose from 5% to 10%",
  "low": 10, "high": 10,
  "unit": "percent",
  "value_kind": "level",
  "of_what": "share of US software workers who lost jobs to AI",
  "baseline": { "number": 5, "period": "2023" },
  "direction": "increase"
}
```

| `value_kind` | Meaning | Example |
|---|---|---|
| `level` | A share or amount at a point in time | "10% of workers lost jobs" |
| `absolute_change` | A change in the same unit (percentage points, counts) | "up 5 points" → unit `percentage_points` |
| `relative_change` | A change relative to the starting value | "job losses doubled", "fell 10%" |
| `unknown` | The source is genuinely ambiguous | "AI job losses up 10%" |

Some notes on these fields:
- **`low`/`high`** handle ranges and approximations ("8–12%", "around 10%"). A single figure sets both to the same number.
- **`of_what`** spells out what the number is a share or count *of*. Two 10% figures about different things should never be compared.
- **`baseline`**, when the source gives one, lets code convert between kinds: 5% → 10% is a `level` of 10, an `absolute_change` of +5 points and a `relative_change` of +100%.

**What the code does (stage 5):**
- It only compares values of the same `value_kind`, or values it can convert using a baseline.
- Two values "agree" if their ranges overlap, or are within a set tolerance.
- `unknown` follows the same rule as an unspecified scope: it can produce a *tension*, never a confident *contradiction*.

## Revised claim format, at a glance

```
claim_id, source_id, question_id, statement
modality       observed | forecast | opinion
certainty      asserted | hedged | reported
causal         null | {cause, effect}
value          null | {raw, low, high, unit, value_kind, of_what, baseline, direction}
scope          {population, geography, timeframe, metric} × {raw, canonical}
evidence       {quote, attributed_to}
grounded       set by code; false → moved to dropped_claims.json
```

## 🤖 Claude

**1. Does a 10 MB cap handle big responses?** Mostly, but only if four details are right. The plan now has a "Size and time limits" section covering them:
- **Count bytes after unzipping.** A "zip bomb" can be 1 MB as downloaded and 1 GB unzipped. If we counted the downloaded size, it would pass the cap.
- **Don't rely on the `Content-Length` header.** We use it to reject early when it says the file is too big, but it can be missing or wrong, so the streaming byte count is the real guard.
- **Limit total time, not just the wait between bytes.** A server can send 1 byte per second forever, and a "wait for the next byte" timeout would never trigger.
- **Give the headless browser its own limits.** It downloads many files per page, so the byte count doesn't apply there. It skips images, video and fonts, uses the same total time limit, and checks the size of the final page.

Also: the cap is now 10 MB for HTML and 25 MB for PDFs, since reports are often larger.

**2. Tagging CAPTCHA and bot-check pages.** Yes. These are tricky because the server reports success ("200 OK") and returns a real page, just not the article. The plan adds a new `bot_challenge` status, kept separate from `blocked` (which now means only an HTTP 403/429 refusal). Detection uses three kinds of signal:
- **Response headers**, e.g. Cloudflare's `cf-mitigated`.
- **Known challenge code in the page** from the main bot-protection services: Cloudflare, reCAPTCHA, hCaptcha, DataDome, PerimeterX, Imperva and Akamai.
- **Phrases** like "verify you are human".

To avoid false alarms, a weak signal only counts if the page also has very little readable text. That way a normal article with a reCAPTCHA in its comment form stays `ok`, and there's a test for exactly that case.

When a challenge is found:
- The record says which service it was, e.g. `bot_challenge: cloudflare`, so the brief can say exactly why a source is missing.
- The browser waits ~5 seconds once, because some challenges clear on their own once a real browser runs them.
- If it's still a challenge, we move to the next method. We never try to solve a CAPTCHA.
- Stage 2's topic check is a second safety net: a challenge page that slips through gets marked `off_topic`.

**4b-1: Code checks.** These are fast and predictable:

## Can one ADK agent run the whole thing, with every stage as a tool?

**Yes, it's possible.** I checked the installed ADK (version 2.12), and it supports this directly:
- **Stages as tools:** an `LlmAgent` takes plain Python functions, including async ones, as tools. Each stage would be a thin wrapper around code that already exists: `plan_research`, `fetch_sources`, `clean_sources`, `extract_claims`, `align_claims`, `judge_claims`, `write_brief`.
- **Running it:** `Runner` / `InMemoryRunner` handle sessions.
- **Guardrails:** there are callbacks before and after each tool call (`before_tool_callback`, `after_tool_callback`, `on_tool_error_callback`), which is where checks like "plan before fetch" would go.

**How I'd build it, if you choose it:**
- **Tools return short summaries, never page text.** For example: "4 sources: 3 usable, 1 cookie wall; 22 claims". The big data stays on disk. As a bonus, the coordinating agent **never sees raw web content**, which removes the prompt-injection risk at that level.
- **The agent makes real decisions, not just "call the next step":**
  - Stop early and write an "insufficient sources" brief if fewer than 2 sources are usable.
  - Re-fetch once after a temporary failure.
  - Re-plan if most claims fall outside the plan.
- **The agent writes the bottom line itself, but has to submit it through `write_brief`, which checks it.** Bullets must cite finding IDs and use no unbacked numbers. If a bullet fails, the tool rejects it with the reason and the agent can fix it and resubmit: a check-and-retry loop inside the agent.
- **A code backstop:** if the agent skips a stage or stops early, plain code runs whatever is missing, so a brief is always produced.

**Trade-offs:**
- ➕ It's real tool use with an agent making decisions, which matches your original ADK idea and the "multi-step agent design" criterion.
- ➖ The order of stages is mostly fixed, so letting an LLM choose it adds unpredictability where it isn't needed. The backstop handles that, but it's extra machinery.
- ➖ **Model quota is the real risk.** Your key has no Pro, Flash has run out of quota today, and only Flash-Lite is working. Flash-Lite is the weakest at multi-step tool calling, and the agent adds 8–12 more calls on a rate-limited free tier.
- ➖ About **45–60 minutes** including the backstop and tests, on an ADK version I haven't used before.

**My view:** it's a sound design and worth doing if you want ADK to be visible in the submission. If time matters more, a plain async runner gets the same pipeline working, and NOTES.md can describe the agent design as the production step. This is your call.

## Which kind of ADK agent should run the pipeline?

There are four realistic options:

| Option | What it is | Verdict |
|---|---|---|
| **A. `LlmAgent` coordinator** with each stage as a tool | An LLM decides which stage to call next | ❌ The order is fixed, so this adds unpredictability for no gain. It costs ~10 extra LLM calls on a key where only Flash-Lite works, and the agent may skip or repeat stages. Its only real decisions ("stop if fewer than 2 sources are usable", "re-fetch once") are simple rules that code does more reliably. |
| **B. One custom `BaseAgent`** running every stage in code | Our Python runner, wrapped in one ADK agent | ⚠️ It works, but ADK adds almost nothing: one opaque agent, no per-stage events, no use of ADK's parallel execution. ADK would be there in name only. |
| **C. ADK workflow agents, composed** | `SequentialAgent[ ParallelAgent[Plan, Fetch], Clean, Extract, Align, Judge, Brief ]`, where each step is a small custom `BaseAgent` calling an existing plain Python stage function | ✅ **Recommended.** Details below. |
| **D. C, plus an `LlmAgent` just for the bottom line** | Inside the Brief step, a `LoopAgent` pairs an LLM writer with a code checker | ✅ **Recommended addition.** Details below. |

**Why C:**
- The pipeline's structure becomes ADK structure, not hidden Python: planning and fetching **run side by side in a `ParallelAgent`**, then the remaining stages run in sequence.
- Each stage is its own agent, with its own events and state (counts, warnings), so ADK's tracing and dev UI show each stage separately.
- It's **deterministic and testable**, exactly like today. Stages that call LLMs keep their own checked calls inside.
- **Stopping early** ("no usable sources") is a few lines of code with `escalate`, plus a final brief explaining why.

**Why add D:** the bottom line is the one place where the job is open-ended language. An `LlmAgent` writes the bullets. A small code agent then checks them: they must cite finding IDs and contain no unbacked numbers. If bullets fail, the checker hands the reasons back for one more attempt, and after that falls back to template bullets. This is ADK's standard **"generator + critic" loop**: the LLM is used where judgment is needed, and code does the checking. It's built for exactly this.

**One trade-off with D:** an ADK `LlmAgent` takes a single model name, so it loses our automatic Pro → Flash → Flash-Lite chain. I'd set it to Flash-Lite, the only model reliably available on your key, configurable in `.env.local`. The checker's template fallback covers any LLM failure.

**My recommendation is C + D:** ADK where orchestration and judgment loops add value, plain Python for the processing.

**How it's put together**
